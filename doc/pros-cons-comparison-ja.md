# ProcessCommander: Pros/Cons 比較

作業の動かし方を選ぶための Pros/Cons 分析です。ProcessCommander を、LLM 標準のサブエージェントや、役割が重なる他の技術と比べます。

[README](../README-ja.md) に戻る。

---

## サブエージェント vs. ProcessCommander

作業を **LLM 標準のサブエージェント** で動かすか、**ProcessCommander が管理する CLI プロセス** で動かすかを選ぶための比較です。

### トークンコストが決め手でなくなった今

以前は、ProcessCommander に作業を任せる一番の理由はトークン使用量でした。今は、監督役の LLM が ProcessCommander のジョブを待つコスト（`taskqueue_wait`、`bt_wait`）と、サブエージェントに任せるコストがほぼ同じです。そのため、選ぶ基準は値段ではなく、**耐久性、決定的な制御、可視性** になります。

| | サブエージェント | ProcessCommander |
|---|---|---|
| **寿命** | 親のターンの中でしか生きない。親の中断、クラッシュ、コンテキスト圧縮、セッション終了で消える。 | LLM のセッションとは別に、ダッシュボードで動く。別のセッションから後で `wait` / `get_state` で拾える。1 時間かかるジョブを投げて席を外せる。 |
| **制御フロー** | 「A と B が終わったら C、2 回までリトライ、失敗したら上に上げる」を、親 LLM が毎ターン推論して回す。間違えることがあり、再現性もない。 | タスクキューの依存関係やビヘイビアツリーに一度書けば、ProcessCommander が決定的に実行する。LLM は計画を書く役と、`escalate` ノードに答える役だけ。 |
| **可視性と介入** | 結果が返るまでブラックボックス。 | ダッシュボードと BT ビューで、全ワーカーの状態と出力をリアルタイムに見られる。いつでも kill、retry、pause、入力の送り込みができる。 |
| **ワーカーの種類** | 同じクライアント内の Claude だけ。 | 他のエンジン（Codex、Gemini/agy、opencode）や普通のプロセス（ビルド、テスト、サーバー）を、同じキューやツリーに並べられる。「レビューは別モデルで」「テストが通ったら次へ」が自然に書ける。 |
| **並列度と負荷** | 親が一度にいくつ呼ぶか次第。 | キューの `concurrency`、優先度、リソースロックで、大量のジョブを投げても暴走しない。 |
| **準備と文脈** | 準備不要。親の会話の文脈をそのまま使える。 | Windows 専用でインストールが必要。各ジョブの指定（プロンプト、コマンド、タイムアウト、成功条件）を明示する必要がある。 |

**目安:** 短くて使い捨てで、親がその結果をすぐ使う作業はサブエージェント。長い作業、失われては困る作業、依存やリトライがある作業、人が見たい・止めたい作業、Claude 以外のワーカーが混ざる作業は ProcessCommander。

### サブエージェント（LLM 標準）

**長所**
- 監督役の LLM と深く統合されている。文脈を共有し、状況に合わせて考え、ツールを使い、途中で計画を変えられる。
- 追加のバイナリや準備が不要。LLM クライアントが動く場所ならどこでも使える。
- 短い推論、コード編集、調査に最適。
- エラーの診断とリトライを、人間に近い判断で自然に行える。

**短所**
- 親のターンとコンテキストウィンドウに縛られる。親のセッションが中断・終了すると消える。
- 長時間、対話型、プロセスツリーの多い作業（ビルド、開発サーバー、TUI エージェント）には向かない。
- 観察手段が少ない。ライブの端末グリッド、アイドル検出、ジョブオブジェクトによるツリー制御がない。
- 並列や依存関係の制御はクライアント次第で、暗黙的なことが多い。
- LLM セッションの再起動をまたいで状態を保持・復元しにくい。

### ProcessCommander（外部 CLI プロセス）

**長所**
- 本物の CLI エージェントやツール（`claude`、`opencode`、`codex`、ビルドスクリプト）を、Win32 ジョブオブジェクトでツリーごと管理する OS プロセスとして動かす。
- ライブのダッシュボード: 最大 16 端末、アイドル検出、ジョブごとのタイムアウト、リトライ、依存関係、永続化されるタスクキュー。
- `.done` マーカーとプロセスごとのログで、LLM や自動化が完了を簡単・確実に検出できる。
- ProcessCommander から起動した Claude Code のサブエージェントも見える。監視ペインに、ステップ、トークン、ツール回数つきのツリーとして表示され、`pcder agent status` でも一覧できる。
- LLM は監督役に徹する。依存、リトライ、分岐（タスクキュー、ビヘイビアツリー）は ProcessCommander の中で決定的に実行される。
- LLM のエンジン（Claude、Codex、Gemini/agy、opencode）と普通のプロセスを、1 つのキューやツリーに混ぜられる。
- MCP と CLI の両方で使え、プロジェクト内にデータディレクトリを置ける。
- 再起動をまたいで状態を復元できる。

**短所**
- Windows 専用。インストールと準備が必要。
- プロセスの中身は比較的見えにくい。LLM が見られるのは取り込んだ出力で、内部の推論ではない。
- タスクの指定（コマンド、タイムアウト、成功条件）を明示する必要がある。
- 運用の複雑さとリソースの負担が増える。
- 対話的にデバッグするにはダッシュボードからアタッチする必要がある。
- サブエージェントについて分かるのはストリームが報告する内容（ステップ、状態、トークン、ツール回数）だけで、推論の中身は見えない。

### おすすめ

**サブエージェント** は、親がすぐ結果を使う短い推論やコード変更に使う。**ProcessCommander** は、並列、長時間、対話型、ビルドの重い CLI 作業に加えて、セッションより長く生き残る必要がある作業、決まった計画どおりに進めたい作業、見ながら操作したい作業に使う。両方のいいとこ取りとしては、監督役の LLM が重い作業を ProcessCommander に任せ、分析や編集はサブエージェントにやらせる。

## その他の選択肢 vs. ProcessCommander

ProcessCommander と役割が最も重なる選択肢の Pros/Cons です。各リストはその選択肢自体の長所・短所で、最後の行に ProcessCommander との違いを書きます。

### Claude Code 組み込みのバックグラウンド実行（`run_in_background`、Monitor）

**長所**
- 準備不要。LLM クライアントに組み込まれていて、何もインストールしなくてよい。
- 完了すると LLM に自動で通知される。ポーリングや `.done` マーカーは不要。
- クライアントが動く場所ならどこでも使える。

**短所**
- セッションに縛られる。クライアントを再起動すると、バックグラウンドのジョブと状態は残らない。
- ダッシュボードがなく、出力は LLM を通してしか見えない。
- 依存関係、優先度、リトライ、アイドル検出、成功条件がない。
- 対話的な入力（ConPTY、TUI エージェント）に対応していない。
- プロセスツリーの後始末はクライアント次第。

**ProcessCommander との違い:** セッション内で長いコマンドを数回走らせるだけなら組み込みのバックグラウンド実行で足りる。ジョブがセッションより長く生きる必要がある、依存関係のグラフになる、対話的に動かす、ライブで見たい、のどれかなら ProcessCommander。

### tmux / screen ベースのエージェント管理（例: claude-squad）

**長所**
- Unix での事実上の標準。成熟していて軽く、スクリプトで操作できる。
- 人間がどのエージェントの端末にもアタッチして、対話的に引き継げる。
- エージェント管理ツールの多くは、エージェントごとに git worktree を割り当てて分離する。
- 端末の切断（SSH を含む）をまたいでセッションが残る。

**短所**
- Windows ネイティブではない（WSL や MSYS が必要）。Windows のツールやツールチェーンを動かしにくい。
- MCP のインターフェースがない。監督役の LLM は `send-keys` / `capture-pane` で画面を読み取るしかない。
- 構造化された出力（JSON）、完了マーカー、タイムアウト、リトライ、依存関係がない。
- ジョブオブジェクトのようなプロセスツリーの制御がない。

**ProcessCommander との違い:** ProcessCommander は「多数のエージェント端末をライブで並べる」形を Windows ネイティブで提供し、さらに MCP / JSON での制御とタスクキューを持つ。Linux / macOS や SSH 越しなら tmux のほうが向いている。

### Claude Agent SDK / ヘッドレス `claude -p` / LangGraph（コードで組むエージェント）

**長所**
- プロンプト、ツール、権限、構造化（JSON）された結果を、プログラムで細かく制御できる。
- 制御のロジック（分岐、ループ、状態グラフ）がコードなので、バージョン管理やテストができる。
- クロスプラットフォームで、サービスや CI に組み込みやすい。

**短所**
- プロセス管理、ログ、タイムアウト、リトライ、復旧を自分で書く必要がある。
- 動いているエージェントをライブで見る仕組みがない。観察手段は自分で作ったものだけ。
- ワーカーは通常プロセス内やヘッドレスで動くので、人間がアタッチして対話的に操作できない。
- 1 つの SDK やベンダーに縛られる。任意のサードパーティ CLI エージェントを使うにはラッパーを書く必要がある。

**ProcessCommander との違い:** SDK はアプリケーションの中に制御を組み込む。ProcessCommander は、既存の CLI エージェントやツールを、新しいコードなしで観察できる OS プロセスとして動かす。組み合わせると相性がよい。SDK や `claude -p` を使ったスクリプトを ProcessCommander のジョブとして起動すれば、依存関係、リトライ、永続化、ダッシュボードが手に入る。
