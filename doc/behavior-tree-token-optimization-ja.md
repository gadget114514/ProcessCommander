# ビヘイビアツリー トークン消費削減ガイド

ProcessCommander のビヘイビアツリー (BT) は、LLM エージェントの自律実行において最大のコスト・遅延要因となる **「ステップごとの会話履歴肥大化と推論ラウンドトリップ」** を根本から解消するために設計されています。

本書では、BT 機能がどのようにトークン消費を抑制しているか、およびエージェントが BT を利用する際にトークン消費を最小化するためのベストプラクティスを解説します。

---

## 1. トークン削減の基本原理（マクロ視点）

### ① ステップ間トークン消費の完全ゼロ化（ゼロ・トークン・オーケストレーション）
* **従来の課題:**
  従来のマルチステップ実行（「ビルド → ログ確認 → 修正指示 → 再ビルド」等）では、1 手順ごとに過去の会話履歴全体＋ツール実行結果を再送・再推論するため、ステップ数に比例してコンテキストが二次関数的に急増（トークン雪だるま現象）します。
* **BT による解決:**
  ツリー定義（JSON）を `bt_start` で 1 度渡せば、ノードの順次実行・並列実行・リトライ・条件判定が **C++ ネイティブ側で自律進行** します。ステップ間での LLM 推論は一切発生せず、中間ステップのトークン消費は **0** です。

### ② 条件判定とリトライのローカル完結
* `exitCode`, `fileExists`, `fileNewer`, `outputMatches`, `jsonValue`, `var` などの判定が C++ 側で即座に評価されます。
* 「ビルドが成功したか」「特定のエラーメッセージが出たか」「成果物ファイルが更新されたか」を LLM がログ全文を読んで判断する必要がありません。
* `retry` / `repeat` による試行錯誤ループも内部で完結します。

### ③ 安全限界（Limits）による暴走・トークン爆発の防止
LLM エージェントの運用で最も危険な「無限修正ループ」を、C++ レイヤーのハードリミットで遮断します。
* `retry.max` / `repeat.max`: 必須指定（1〜100）
* `limits.maxNodeRuns`: デフォルト 200 回
* `limits.maxWallSec`: デフォルト 24 時間
エラー時に LLM が無限にリトライを繰り返して大量のトークンを浪費する事故を確実に防ぎます。

## 2. API レスポンスのトークン最適化（ミクロ視点）

BT API は、LLM がコンテキストを無駄に消費しないよう、返却ペイロードが徹底して軽量化されています。

### ① `bt_wait` の `compact: true` によるツリー JSON 省略
* **機能:**
  `bt_wait` の呼び出し時に `"compact": true`（CLI: `pcder bt wait --compact`）を指定すると、完了時やエスカレーション時に数千〜数万トークンになり得る `tree` JSON 全文の返却を省略し、ステータスと 1 ノード 1 行の `compact` サマリのみを返します。
* **効果:**
  1 回の待機完了あたり **数千〜数万トークンを削減** できます。完全なツリー定義・状態が必要になった場合のみ `bt_get` を呼び出します。

### ② タイムアウト時応答の最小化
* ロングポール（`bt_wait`）が待機タイムアウト（進捗のない途中経過）で返る際、ツリー構造を一切含めず、最小限のメタデータ `{ok, id, state, detail, version, nodeRuns, timedOut: true}` のみを返却します。ポーリングループによるコンテキスト浪費を防ぎます。

### ③ `escalate` 判断パケットのデータ絞り込み
途中で人間の判断や上位 LLM の指示を仰ぐ `escalate` ノードでは、判断に必要な情報だけを局所化して送信します。
* **ログ行数制限 (`lines` / `logLines`):**
  `include.logs` のログ末尾行数はデフォルトで 100 行に制限されます。さらに `include: { "logs": ["build"], "lines": 30 }` のように任意で小さく指定可能です。
* **ファイルサイズ制限 (`maxBytes` / `fileMaxBytes`):**
  `include.files` の読み込みサイズはデフォルトで 16 KB に制限され、超過部分は `...[truncated, N bytes]` として切り詰められます。
* **変数値のプレビュー切り詰め (`BtVarPreview`):**
  全変数一覧（`pktJson["vars"]`）に含まれる各値は 200 バイトに切り詰められます。判断に全文が必要な変数のみを `include.vars` に指定することで、無駄なコンテキスト消費を防ぎます。

### ④ ノード定義内プロンプト等のエコーバック抑制
* 完了時などに `tree` を受領する場合でも、各ワーカーノードの長大な `prompt` や `instructionsText` は自動的に 200 バイトにトリミングされます。LLM 自身が登録時に送信したプロンプトを完了時に再読受領する無駄なトークンを排除します。

### ⑤ ワーカーの構造化出力とファイル連携 (`outputSchema`)
* ワーカー LLM の出力は環境変数 `PC_BT_RESULT_FILE` 経由で一時ファイルに出力させ、`outputSchema` で検証します。
* 会話コンテキスト経由でのやり取りに伴う「前置き文」や「書式崩れによる再試行」のトークンを削減し、後続ノードからは `${node.output.<field>}` でピンポイントに必要な値のみを展開・参照できます。

## 3. トークンを最小化する BT 作成のベストプラクティス

LLM エージェントが BT を登録・運用する際は、以下の点に留意してください。

1. **`bt_wait` では常に `compact: true` を指定する**
   ```json
   { "action": "bt_wait", "id": "my-bt", "compact": true }
   ```
2. **状態判定にログ読解を使わず、条件ノードを活用する**
   - ログ全文をプロンプトで読む代わりに、`outputMatches`（ログ正規表現マッチ）や `jsonValue`（JSON 判定）を使う。
3. **`escalate` の `include` を必要最小限に絞る**
   - 判断に直接関係のないノードのログや巨大ファイルを `include` に含めない。
   - `lines: 30` や `maxBytes: 4096` を明示してパケットを極小化する。
4. **適切な `limits.maxNodeRuns` を設定する**
   - ワークフローの想定ノード数に応じた上限（例: 20〜30 回）を指定し、万が一の過剰ループを早期防止する。
